# B3: parallel runtimes

**The 2.96× mixes two modes** (tsrsG1 against tsrsN). The scaling agent's runs on pup (CPUs 0-2,5-11, `perf-scaling/stat.*`) give, within one mode: tsrs 0.660 → 0.210 s (3.15×), trig 1.228 → 0.504 s (2.44×). Both run **4 checkers** (tsrs: `checkerpool.rs:1944-1975`; trace threads checker-0 to checker-3).

## tsrs
- **Threads and memory:** one OS thread per checker, 512 MB stack (`checkerpool.rs:151-186`). Checkers share only the frozen program. Each thread has a bump arena it never frees, with THP (`arena.rs:1`, `allocator.rs`).
- **Balance:** checkers get locality groups (`:2039`). Each has a queue of files, front and back packed in one atomic; idle checkers steal from the back of the fullest queue, and heavy files go first (`:1208-1257`, `:1374-1385`, `:1515`).
- **Front end:** parse and bind run on a rayon pool, one thread per core (`program.rs:498-518`, `filesparser.rs:926`).

## Trig at 4 checkers
From the scaling agent's `perf sched timehist` (`th.trigN.txt`):
- **Front end:** 0-54 ms on one thread. tsrs takes about 20 ms.
- **Checker CPU:** 446, 318, 284 and 257 ms. The slowest is **1.37× the mean**. The cause is tsc's static FENNEL assignment, with no stealing (`declarations/checkerpool.rig:79-116`).
- **Tail:** about 15 ms.
- **CPU growth:** +10% for Trig against +12.5% for tsrs. Duplicated work is alike in both.
- **Rig's scheduler is not the loss:** 848 context switches against 715 at one checker. At most half the workers search, and idle workers sleep (`sched.zig:1795-1800`).

So imbalance costs about 95 ms and the serial front end about 34 ms. tsrs in Go mode, with the same static assignment, scales 2.66×.

## Ranked (ts-pattern, wall 504 ms)

| # | change | owner | win | cost |
|---|---|---|---|---|
| 1 | Canonical-history mode with file stealing and heavy files first (tsrs `:1208-1257`, research 11 §3.2) | Trig | about −90 ms (**−18%**) | Large. **Owner's call:** output equals `tsc --checkers C` only where tsc's doesn't vary with C. G1 found it doesn't vary on all 6 projects |
| 2 | Parallel parse and bind (`par.map`, largest file first; binder atoms per task, as G3) | Trig | about −34 ms (**−7%**), exact | Medium. 11% of the wall at 4 |
| 3 | `par` with per-task state (k workers, each holding a checker, pulling items dynamically) | Rig | enables #1 | Medium |
| 4 | MADV_HUGEPAGE on segments, or prefault for busy task heaps. Prefault turns off at the second heap (`alloc.zig:56-60`): 94k faults against tsrs's 19k | Rig (`table-hugepages`) | 2-6% (tsrs `mem-no-thp.md`). G9 measured ±2% on E-cores, so measure on P-cores | Small |
| 5 | Smaller data: LLC misses +49% against tsrs's +30% under concurrency | Trig + Rig | about 3% | Planned |
| 6 | Teardown by exit (G8); pin checker tasks (one moved worker) | Trig | ≤2%, ≤1% | Small |

#1 and #2 together: about 380 ms, 3.2×. Scaling then matches tsrs's, but the one-thread gap (1.76×) still decides.

**Literature:** Go and Tokio (run-next, steal half, capped spinners) are what Rig already does. rustc's parallel front end, esbuild and tsgo/Bun win by fine work units (files, queries), not by their schedulers.
