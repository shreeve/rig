## 2. Is there a phase B with no Table per Ast?

**Phase A's mechanism needs a capacity known at compile time.** A
phase A lookup is `table[id & MASK]`: one `and` with a constant keeps
any id inside the table's reservation, so the read is memory-safe with
no test. A List's capacity changes as it grows, so masking it means
loading the capacity, which costs what the check costs. That is why
phase B reached for a Table per Ast.

**One program-wide node Table, each file a range (tsrs's arena):**
- **Parse tasks cannot write it.** Files are parsed in parallel tasks,
  and safe Rig has no way to lend disjoint windows of one table to
  several tasks. That would be a Rig feature: a table split into
  disjoint writable ranges, like a slice split.
- **Copy after parse:** each file parses into its own List as now, and
  the main task copies the file's records into the program table at its
  base (the checker's `node_base` already numbers nodes this way), then
  frees the List. Memory is level apart from one file's transient
  copy. The cost is the copy: about 0.5–0.7M nodes of 24 bytes (about
  14 MB, estimated from 78k lines), roughly 1.5 ms, which is 0.2% of
  ts-pattern's run and 0.9% of zod3's. Against the node records' reach
  (0.42% and 1.37% of cycles), that nets about 0.2% and 0.5%.
- **Lines:** an Ast cannot hold a loan of the program's table, so every
  accessor generated by `tools/ast/gen.py` would take the table as an
  argument. That means 491 generated sites, every caller (the parser
  and binder keep reading their List until the copy), and the checker's
  `files[f].ast` paths. Estimate 800–1,500 lines of Trig, mostly
  generated, and a second accessor set for the parse phase.
- **Not worth it now.** The net is under the bar, for a large change.

**Files:** `Program.files` is a `List[ast.File]`. A made Table at
Trig's `FILES = 2^19` would build 524k default files up front. A
bounded file table (2^12–2^14 files, made, each slot an empty `File`)
would fit in memory, but caps the program's size. Its reach is 0.09%
and 0.74% of cycles. **Not worth it alone.**

**What would cover all of it** is the language rule the item began
with: ids typed by the table instance they came from, so a List's push
gives an id its reads need not test. Ids read from records (node ids in
`words`, a file index in a `NodeRef`) would still need a test, or a
mask, where they enter the type. This is the CORE review route
(beat-tsrs item 5), and it is the only one that reaches the 1.6–2.1%
spread over Lists.

## 3. Do packed spans (item 19) cover the span part?

**No, they are separate.** Item 19 changes how a span object is held
(one word: it removes store-forward blocks). The span part here is the
range test on `type_lists[list.start + k]`, which packing leaves. They
would stack. The span part is small: 0.89% of instructions with level
cycles on ts-pattern, and 0.63% / 0.49% on zod3.

## Defaults

1. No phase B as Tables now. The node records' net is about 0.2–0.5%
   for 800–1,500 lines.
2. Keep the ceiling's remaining 3.7–5.0% of instructions (2.3–3.9% of
   cycles) for the language rule's design round: ids typed by their
   table, checked or masked where they come in from memory.
3. Spans ride with whichever of 2 or item 19 lands; they are not a
   change of their own.
