# Review of Rig PR #684, `par.workers` (head 22a3e59bf)

Read-and-probe review, Mac only. Build: detached worktree
~/Data/Code/worktrees/rig/review-684 (`tools/heavy zig build`); base for
comparison c2639a40f (merge base, worktree since removed). Probes (not kept)

## Verdict: fix first (finding 1; 2 and 3 are small and belong in the same round)

## 1. HIGH: a state's write view escapes into the result (`|s, x| s`)

`typecheck.parWorkers` takes `value = readValue(...)`, which keeps a
`!S` when S does not read as a value, and the `.moves` crossing check
lets a write view through. So for a state that owns a resource the
result is a `List` of write views (Zig `List(*Acc)`), one per *item*,
and every item a task took gives a fresh `!` to the same state.

d5_escstate_named.rig:

```rig
use std.par
obj Acc
  seen: List[Int]
sub main()
  states: List[Acc] = List()
  !states.push(Acc(seen: List[Int]()))
  items = List([1, 2, 3, 4])
  ys = par.workers(!states, ?items, |s, x| s)
  print(ys.len)
  !ys[0].seen.push(7)
  !ys[1].seen.push(8)
  print(states[0].seen)
```

Output: `4` then `[7, 8]`. Four live `!Acc` to one object; the
writes through ys[0] and ys[1] both land in states[0]. The loan checker
keeps `states` lent for as long as `ys` lives (d6: reassigning `states`
is rejected), so it's no use-after-free, but `!` is no longer exclusive.

Using it in parallel reaches Zig rather than a Rig error.
d11_alias_race.rig (the same, then
`par.workers(!ys, ?work, |v, y| v.n += 1 ...)`) and d8 (`par.each(!ys, |v| ...)`) both give
`error: type '**__rig_main.Acc' does not support field access`. Only
that Zig error stands between this and two tasks writing one Acc.

With a temporary for the items (`?[1, 2, 3]`), the same closure gets an
error that misleads: "a view of the temporary `[1, 2, 3]` outlives its statement".

For a state that copies (`obj Acc n: Int`), the emitter returns `s.*`
(copies), so no aliasing there (d10 prints 0, which is correct for copies).

Fix: reject a value that is, or holds, a write view (`par.workers gives
back each call's value, and `s` is the task's state lent to write: copy
it out, `+s`, or give a field`). A read view of an item (`|s, x| x`) is
fine: it keeps `items` lent to read (e3).

## 2. MEDIUM: the named-function fix misses a scalar's write view

The fix checks `have != given and have != readValue(given)`, and
`readValue` also strips a `write_view` of a scalar. The runtime passes a
pointer for `!x`, so a function taking the scalar by value passes the
checker and fails in Zig:

- named/n12: `fun step(s: Int, x: Int) -> Int`, `par.workers(!ints, ?xs, step)` gives
  `tasks.zig:1128: expected type 'i64', found '*i64'`
- named/n3: `sub show(x: Int)`, `par.each(!xs, show)` gives
  `tasks.zig:1051: expected type 'i64', found pointer` (the same on base)

Fix: apply `readValue` only to read views (the item, and map's
element), never to `par.each`'s element or `par.workers`' state.

"Rejects nothing valid": checked against base. Every function name the
PR now rejects (n1 `?Int` for `!Int`, n8 `Acc` by value for `?Acc`, n13
`String` by value) failed in Zig on base too. n4, n5, n6, n9, n15, n16,
and n2 still run. n10 (`?Acc` state for `!Acc`) is new to workers and
rejected; it would be valid as a plain call (n14 shows `!Acc` passes to
`?Acc`), so the rule is stricter than it needs to be, but it can relax later.

## 3. LOW-MEDIUM: a false "stores a view of `xs` in `states`" error

When `states` is a `![]S` parameter, every `par.workers` call in the
function is rejected:

l8_workers_local_slice.rig:

```rig
fun run(states: ![]Acc, xs: ?List[Int]) -> List[Int]
  par.workers(!states, ?xs, |s, x| x + 1)
```

`error: \`run\` stores a view of \`xs\` in \`states\`, which its caller
reaches, but its signature does not keep \`xs\`; say so: \`keeps xs\``

The call cannot store an item in a state (e2: `s.keep = x` is rejected,
and states must be sendable). A user function of the same shape,
`g(a: ![]Acc, b: []Int)` (l7), is fine, and `!List[Acc]` parameters
(l5) work. The call type `noteCallee` records probably needs to say
that it keeps nothing.

## Checked and sound

- Aliasing is rejected: `!xs, ?xs` (a), `|?states|`/`|+states|` capture
  while lent (b, b2), `|?box|` with `!box.states` lent (s_capbox),
  storing an item view in a state (e2), moving out of a state (d4), and
  cloning out via a field (d3, asks for `+`). `|+c|` of `*Cell[Int]` is
  accepted, which is right (atomic one-word Cell, SPEC §10).
- Queue: one `fetchAdd` per item, distinct `out[i]`/`made[i]` slots, and
  joins by `wait`. After `failed`, at most one more item a task, whose
  value is marked and dropped. No race found.
- Failure (f1): Bad.odd, values dropped, states usable after, sanitizer
  clean, no leak. Deadline (m_deadline): `Stop.timeout`, clean.
  Panic under `task.isolate` (f2, f3): `Stop.panicked`, only "left by a
  panic" allocations, as SPEC says.
- Cancel latency: the caller is never canceled. A helper's failure
  waits for the caller's current item (f1: 347 ms for a 300 ms item 0).
  It's the same as `parRunInto`, so not new; worth a SPEC line someday.
- Determinism (h_seeds, `rig test --seeds=20` twice): per-state
  counts/sums and the results are identical run to run for each seed,
  and they differ across seeds. The calling task takes its share (state 0
  got 7–16 of 40 items).
- Nested `par.workers` inside a body (k_nested) works.

## Empty-states panic

Keep the panic. A zero-length state list is known at compile time only
for a literal or a fixed array, which is rare. It's a programmer error,
like an index out of range, and `[]` states with `[]` items still gives
`[]`.

## Minor, pre-existing (not this PR)

- A closure with `return Bad.odd` is not inferred as fallible, for `par.map`
  too (f0: "expected `Int`, got `Bad`").
- A slice parameter declared `?[]Int` is not accepted by par.map or par.workers
  (`[]Int` is the read slice).
