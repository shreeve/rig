# sanstun port: the curve-and-hash expert's report

The timing table is [results-final.md](results-final.md); the constant-time results (`ct/results.txt`) and the sources are on pup in `/zfs/trig-pup/records-data/rust-ports/sanstun/panel/curve-hash/`. The full detail is in the appendix below.

**Numbers.** Apple M5, 9 interleaved rounds, fastest of each, load average 6 to 7 (two other experts were running). Rig is built with main's rig (6c150dfa8). The DIT bit is on in every column, because only that setting passed the timing test (below).

| case | dalek / blake2 | Zig ceiling | Rig fast | Rig safe (no DIT) |
|---|---:|---:|---:|---:|
| pub | 7.72 µs | 5.45 µs | 5.38 µs | 5.51 µs |
| dh | 19.80 µs | 14.96 µs | 15.05 µs | 15.69 µs |
| h32 / h64 / h128 | 80.3 / 81.9 / 148.2 ns | 70.6 / 69.2 / 139.6 | 71.3 / 71.6 / 142.7 | 72.7 / 79.9 / 145.4 |
| hmac16 / hmac32 | 299.3 / 300.1 ns | 286.1 / 287.2 | 290.1 / 289.3 | 293.4 / 294.1 |
| mac128 / mac1024 | 226.9 ns / 1.30 µs | 215.9 / 1.20 µs | 213.0 / 1.22 µs | 222.7 / 1.29 µs |

- **Against Rust:** Rig is 1.43× as fast as dalek on public keys (a fixed-base comb with a NEON table select) and 1.32× on DH. It is 3% to 14% faster than blake2.
- **HMAC with a reused key:** computing the pads once makes each MAC 2.1× as fast (144 ns).
- **Against the ceiling:** Rig matches it on the curve and is 1% to 4% slower on BLAKE2s.
- **Zig std:** its public key is a ladder, at 19.3 µs.

All of these pass the RFC 7748 vectors (including the iterated chain), RFC 7693 appendices B and E, and WireGuard's construction and identifier hashes.

**Constant time.** I ran dudect-style tests: 200,000 calls per run, fixed against random secrets.
- **Without DIT, every X25519 fails, dalek included.** dalek reaches |t| = 43; the bar is 4.5.
- **With PSTATE.DIT set, every one passes.** |t| stays at 2.3 or below.
- **The test is trustworthy.** Fixed-against-fixed and random-against-random runs pass, and a ladder that swaps by a branch fails at |t| = 85.
- **sanstun as shipped is not constant time on Apple silicon** by this test, because neither dalek nor ring sets DIT.
- **DIT costs 0% to 1.5%.**

**Top three Rig gaps:**
1. **DIT can't be set from user Rig.** There's no inline assembly and only std may use `extern zig`. std.crypto's Zig shim must set and restore it around each secret operation, and the same shim should provide `wipe` (`secureZero`) and a value barrier.
2. **`--release` keeps overflow checks on secret limbs.** That is 167 never-taken branches in the comb, a cost of 1% to 5%. std.crypto should use wrapping operators, or Rig needs a "proven, unchecked" form.
3. **There's no fixed-size view of part of a slice** (`b[at..][..64]` as `?[64]U8`). The 16 checked reads per block cause BLAKE2s's 1% to 4%.

**Recommended API.**
- **X25519:** `crypto.x25519.Secret` (owning, wiped on drop) with `s.public()` and `s.share(peer)!`. A low-order key fails with `KeyError.low_order`: "x25519: the peer's key has low order, so the shared secret would be zero".
- **BLAKE2s:** `blake2s.hash(data)`, `blake2s.mac[n](key, data)`, and `Hasher` with `!h.add(x)` and `<h.done()`.
- **HMAC:** `blake2s.hmac(key, data)`, plus `blake2s.Hmac.of(key).mac(data)` for a key used again.
- **Helpers:** `crypto.wipe(![]U8)` and `crypto.equal`.

**Mishap.** A copy command with an empty variable copied 93 GB of the filesystem into `ct/rigdit/`. I killed it and deleted the copy; nothing outside my folder was touched. A later cleanup with `rm` inside `sh -c` was refused by a safety check, and I rebuilt without it.

**Appendix: the full REPORT.md content, since the file couldn't be written**

*Ceiling designs*
- **Field:** five 51-bit limbs with u128 products (25 per multiplication, 15 per squaring); a difference adds 2p first; inversion is Fermat's.
- **Ladder:** about 66k cycles, limited by the multiplier's throughput.
  - What's left to try: radix 2^64 or NEON with 2^25.5 limbs. I tried neither.
- **Comb:**
  - Signed radix 16, 64 mixed additions, 4 doublings and one inversion.
  - A 30 KB table generated by `gen_table.zig`, which checks the base point is on the curve and maps to u = 9.
  - Reading each row as NEON vectors took it from 6.95 to 5.3 µs.
- **BLAKE2s:** scalar, fully unrolled, latency bound at 240 cycles a block.
  - What didn't work on the M5:
    - `@Vector` rows: 2.5× slower.
    - Folding rotations into `eor` with `ror`: 15% slower.
    - Reassociating the adds: no change.
  - What won: one-shot hashing straight from the input (h32 went from 93 to 70 ns), and HMAC with the pads computed once.
- **Limb bounds:** the Rig debug build, with every operation checked, passes all vectors.

*Constant-time plan*
- **Today:** Rig states constant time only by how the code is written: mask swaps, whole-row table reads, no secret branches or indexes.
- **How to check:**
  - The disassembly via `ct/dis.sh`: the fast build has only loop-counter branches.
  - dudect via `ct/run.sh` and `ct/ttest.py`.
  - The emitted Zig, which matches the ceiling line for line.
- **What Rig lacks:**
  - DIT.
  - Unchecked arithmetic on secret limbs.
  - A value barrier.
  - Later, possibly a `secret` marker the checker enforces. That would be a CORE change for the owner.

*Zeroizing*
- A secret is an owning `obj` with a `drop` body that calls `crypto.wipe`. It moves rather than copies.
- Register and spill copies can't be wiped (Rust's zeroize has the same limit). So secrets should never travel as plain `[32]U8`.

*Smaller gaps*
- `a.mul_wide(b)`: works today as `U128(a) *% U128(b)`.
- `x.rotr(n)`: the shift-or idiom works.
- A `[]U8` view of a `?String`.
- Lending a temporary to a `?[32]U8` parameter.
- `sub` is a keyword, so the field difference is named `fsub`.

*Other API candidates*
- **X25519 B:** `Key`, `public`, `agree` returning `Shared`, error `KeyError.weak`.
- **X25519 C:** functions `x25519.public_key(s)` and `x25519.dh(s, peer)!`.
- **BLAKE2s B:** `keyed`, `State` with `update`/`final`.
- **BLAKE2s C:** `digest`, `Stream` with `push`/`finish`.
- **HMAC B:** a generic `crypto.hmac[H]`. It needs an API for hashes.
- **HMAC C:** `blake2s.auth`. It's ambiguous with keyed BLAKE2s.
- **Key-length error:** "blake2s: a key holds at most 32 bytes; this one holds 40".
