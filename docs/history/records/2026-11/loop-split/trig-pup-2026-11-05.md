## What it shows

- **Trig is slower with the split:** 1.7 to 3.0% more instructions on five of six projects, and 0.7 to 2.7% more wall time on four (ts-pattern 1.9%, zod3 2.7%). The A/A arm agrees with split. It does not clear Trig's bar, and it may not land so.
- **On arm64 the split is a clear gain; on x86 it is mixed.** The x86 inner loop is clean (and LLVM unrolls it eight ways), and `even-par` takes 13% fewer cycles, `alloc-par` 17% fewer, and `hog` is 26% faster. The `-tasks` rows above (`even-tasks`, `tree`, `alloc-tasks`) are not results: a profile of `even-tasks` with no release build compiling beside it ([profile-2026-11-05.md](profile-2026-11-05.md)) took 27% fewer instructions and 2.7% more cycles with the split, not 56% more, so this run's `-tasks` rows measured the build that shared the machine.
- **signal** (no checks) is 1.0 to 3.9% fewer instructions and up to 3.2% faster than base on every project: the cost of the checks Trig pays today.

## Next

Profile on pup before any change. `perf` on ts-pattern, base against split, shows where the extra instructions are: the blocks' per-entry cost on short loops, or code the clean inner loops let LLVM add (vectorized and unrolled loops with their prologues, costly on short trips). `even-tasks` on x86 shows what a yield inside a block costs there. Then decide among a cheaper entry, splitting only loops long enough to gain, or arm64 only.
