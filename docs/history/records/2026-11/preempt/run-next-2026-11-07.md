# Four "run next" slots: hog's first step under signal preemption (2026-11-07)

## The stall
`bench/tasks`' `hog` keeps every core busy with 32 CPU tasks. Then, for 50 steps, it queues a 1M-step task, makes two tasks and waits for both. On the Mac with `RIG_PREEMPT=signal`, its first step took 19-134 ms, against 0.3-0.4 ms with yield checks (question 1 of [design.md](design.md), "Hog latency").

**Why the first step waited:**
- Main makes three tasks per step and waits for each in turn.
- With one "run next" slot, each new task pushed the one before into the ring, behind the unstarted hogs.
- The task main waited for therefore ran only after each hog ahead of it was stopped by the monitor.
- macOS coalesces the monitor's 50 µs sleep into 2-3 ms looks, so each hog ahead cost two looks.

## The change
A worker holds four fibers to run next, newest first (`sched.Worker.lifo`):
- The slots are a circle, and `lifo_head`, which only the owner writes, marks the newest.
- A fiber made ready takes the slot after the newest, which holds the oldest or nothing, by one swap, as one slot took. The oldest it displaces goes to the ring, and wakes a worker as before.
- The worker takes the newest, at most `lifo_limit` (3) in a row, as before.
- A thief takes the oldest: `stealNext` after 3 µs, and `takeNext` for a yield check told work waits.
- A waiter hands its worker straight to a task that has not started and is still in any slot (`handoff`).

So a fiber that makes a few tasks and waits for each runs them at once, past the ring. Ownership is as with one slot: whoever moves a slot from a fiber to null by one atomic step owns that fiber. The handshake with the `waiting` flag reads every slot.

## Measured (`--release=fast`)
**hog** on the Mac (M5, 10 workers), fastest of 10 interleaved runs:

| | main | branch |
|---|---|---|
| signal: first step | 19-134 ms | 0.1-0.7 ms |
| signal: whole run | 26-148 ms (best 9.17 ms) | 0.01-0.26 ms |
| plain: whole run | 4-9 ms (best 4.20 ms) | 0.01-0.22 ms |

The checksum is 352345 in every build.

**Three versions, measured in turn:**
1. **Each wake moved the slots down,** up to four swaps. On pup with one worker, `spawn` was 15.9% slower (13.4% with signals).
2. **A circle, one swap per wake.** `spawn` came to 3.2% slower, but `chain` was 7.1% slower: a waiter tried a compare-and-swap on each slot in turn, and those that failed are locked operations.
3. **The waiter finds its slot by plain loads, then does one compare-and-swap.** The tests of whether any slot is held read all four slots and test their union. On the Mac with one worker, `spawn` takes 1.6% more instructions than with one slot.

The A/B harness ran 10 interleaved rounds on pup at one worker, plain and with signals. It put `spawn` 3.3% slower plain and 1.5% slower with signals, and `chain` 2.2% slower plain and level with signals. Every other row was level or faster. The Mac's `spawn` moves about 25% from run to run, main's included.

**Trig 88b06ea** on the Mac, measured on the first version (the later ones change only which slot a wake takes and how a waiter finds its task). Five arms (main plain, an A/A copy, branch plain, main signal, branch signal), 20 rounds, ts-pattern and zod3, exact and balanced, at 1, 4 and 8 checkers:
- **Instructions:** within 0.2% of main on every row but zod3 balanced at 4 checkers, which is 1.2% more plain and 0.9% more signal. Balanced mode's split differs from run to run.
- **Wall time:** the A/A arm differs from main by up to 6.2% under that load. No branch row is further from main than its A/A.
- **Peak memory:** within 1% except ts-pattern exact at 4 checkers, 3.4% less.

**Gates on 6958fd253:** Trig's light gate on pup passed, GREEN, 46 jobs, as did `zig build test` on pup in debug, safe and fast.

**Fairness:** `test/cli/run_next_fair.sh`. A producer that makes tasks forever, in batches of eight it waits for, cannot keep an older task waiting in the ring. The older task runs within 2 s on 1 and 2 workers, plain and signal, in about 22 ms a run, on both main and the branch.

## Seeded runs
Seeded runs (`RIG_SEED`) put every woken fiber on one ready list and never use the slots, so `seeds: 20` covers none of this. The stress scripts `run_next_lost.sh` and `run_next_fair.sh` do. A seeded model of the slots is in the backlog.
