# Zig expert: five close calls

**1. `!` on a call `for` source: AGREE.** In Zig, the loop's mode lives on the capture (`|x|` vs `|*x|`), and whether a write is possible comes from the source's type (`[]T` vs `[]const T`). A call's self mode comes from the method's signature. Nothing does both jobs. Today Rig's `!` does both jobs, and only for a `for` source: `?b.each()` means "lend self", while `!b.counter()` means "loop mode". That is a pun, and the AI reading the code has to remember the exception. So the sigil on a call should always go to the call's self. For a call source, the loop's mode should then come from what the call returns, as in Zig. A returned `!List` view gives write views of the items, a made List is consumed, and an iterator is advanced. `for x in !xs` keeps the write mode, because `xs` is a place, not a call. The old error should name the new reading.

**2. `collect` of views: AGREE.** In Zig, an `ArrayList(*const String)` of pointers into another list is ordinary, and it is the cheap thing to do. Forcing `+x` turns one allocation into N+1 hidden ones, and that breaks the cost model the chain promises ("no allocation but `collect`'s"). The checker already keeps `names` lent while the list lives, and the oracle agrees, so the program is sound. One fix to make: when someone writes to `names` while the collected list lives, that error should offer `.map(|x| +x).collect()`. The fix moves from where the list is built to where a write conflicts with it, and that is where the user needs it.

**3. Check-speed guard as a gate: AGREE.** Zig keeps a perf dashboard of the compiler's own speed because, without one, compile-speed drift goes unnoticed; Rig's 27% drift is that story. A retired-instruction count is the right tool for spotting drift: it is deterministic and does not care about machine load. It needs a stated tolerance, and an `--update` that must say why, the same as json, hash and text. Two caveats: run it only on PRs that touch `src/`, and since `guard.py` runs only on macOS, add a `perf stat` version for pup later.

**4. Dedicated check-speed round after phase 2: AGREE.** Phase 2 moves code around, so tuning before it would be wasted. Once item 3's gate stops new drift, one round can win back the 12% for good. Measure it on Trig's real `rig check` (time, interleaved) as well as the guard's instruction count. Record a budget for each pass, so that a feature's cost of about 1% is visible in its own PR.

**5. Two write captures in `task.select`: AGREE.** Rust rejects two live closures that each hold `&mut n`, even if only one is ever called. Zig would let both `*Int` pointers exist, and it promises no safety for that. Rig promises safety, and main crashed here. Since every arm's closure exists at once, two write views of `n` live at once, so reject it. The workaround (each arm returns a value, and `n` is written after the select) is explicit and costs nothing. A later fix could lower the arms as branches of a `switch` on the arm that won, not as closures. Then each arm's write to `n` would be one branch's write, as with `if`/`else`. That is a change to how select is emitted, not to the ownership rule, so it can wait.
