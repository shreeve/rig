# Designer (Swift ownership, Ruby readability): five close calls

**1. AGREE.** Everywhere else `!b.f()` means `(!b).f()`; the parser itself rewrites `!x.v.push(1)` that way. A reader who knows that one rule reads `for x in !b.counter()` as "lend b to write, call counter", and today Rig quietly gives the mark a second meaning. I checked: main rejects the form with "write `(!b).counter()`", and that workaround runs. So the fix is to make the plain spelling mean what the error message already suggests. One more step finishes the job. For a call source, the loop's mode should come from the result's type, never from a second mark. A `-> !List[T]` result is walked with write views and a made `List` is consumed. That leaves `for x in !xs` with exactly one meaning: a place walked for writing. Swift has no `for inout` at all (you write `for i in xs.indices`); Rig's form is better, as long as the mark keeps one meaning.

**2. AGREE, with a condition.** Ruby's `select` returns the same objects, not copies, and Swift's `filter` "copies" cheaply through copy-on-write. Neither makes the user pay for a deep clone, and Rig shouldn't either. Here is the catch I found by running it: `vs = names.filter(f).collect()` is accepted unmarked and keeps `names` lent. The `!names.push` two lines later then fails, with the note pointing at the chain. But `h = head(names)` is rejected with "write `head(?names)`", and QUICK teaches `xs = ?b.all()`. Bare `find` behaves the same way. My condition: a chain whose result holds views is written `vs = ?names.filter(f).collect()`, by the same rule as any call that keeps its argument lent. Zero-copy is good, and the lasting loan should be visible where it starts. The SPEC should say both.

**3. AGREE.** Slow compiles are Swift's most lasting complaint (the type checker's "expression too complex"). Unguarded drift costs users more than any single feature saves. An instruction count is noise-free, so it can be a hard gate, with a `--update` commit that says why, as the other guards have.

**4. AGREE.** Make the cut after the feature set stops moving, and measure on Trig's real 2 s check, not on the generated program alone. Otherwise the round tunes the benchmark.

**5. AGREE, with a better path for later.** Swift would accept this. Its law of exclusivity counts a non-escaping closure's access only while the closure *runs*, and select runs one arm. But Rig's Core, like Rust, makes a `!n` capture a write view the closure holds for its whole life, and the Core is fixed. Two such views at once broke that rule and crashed, so keep the rejection. The human cost is real: select is exactly where "only one runs" is guaranteed, so people will hit this error. The error should show the value-returning rewrite. A later fix within the Core: the select takes the loan once, `task.select(!n, a.on_recv(|n, v| ...), ...)`, and hands the single write view to whichever arm runs. That keeps one write view and one place it starts, and it fits in a paragraph.
