# Audit: `brackets` branch, emitter correctness and code review

Branch `brackets` (6df0c48..deb11a4), reviewed against the existing
`bin/rig`. Lens: (A) accept means correct in `src/emit.zig` for
compile-time parameters and generic functions; (B) code review of the
source diff.

Method: about 90 probe programs covering every call form in the brief,
each run as `rig check` then `rig run`, with `rig emit` read where the
output mattered. Base behavior was checked with a scratch build of
6df0c48 (with `pre` syntax) to tell regressions from older bugs. Each
finding below was reproduced at least twice with different programs.
Fixes for F2, F3, F4, and F1 were built in a scratch copy of the repo.
With them, the full `./test/run` passes (1247 passed, 0 failed) and
every repro passes. `zig build test` passes on the branch as is.
Regenerating the parser from `rig.grammar` with `../nexus/bin/nexus`
gives the checked-in `src/parser.zig` byte for byte, with no conflicts.

## Clean

These held up under direct probing: the emitted Zig compiled, ran, and printed the right thing, leak-free where resources were involved.

- **Call forms with compile-time and type arguments:** free functions (inferred and explicit), methods on a value, methods through a type (`Tagger.show(?t, 2.5)`, `Cup[Int].put[Int, 1](!c, 5, x)`), `Box[Int].make[String](...)`, `Box.make[Bool](...)`, generic methods on generic types, associated functions with ct values, statement calls (`show[3]`, `Box[Int].st[3]`, `hello[Int]`), and paren-free calls (`show 3`, `report[.strict, 2] "x"`, paren-free with hoisted failing arguments).
- **Hoisted calls with failing arguments:** including write receivers, consumed temporary receivers (`<Cup(v: 3).into[Res](mkres(9)!)`), and a receiver passed as an argument through the type.
- **Keyword arguments and defaults mixed with brackets:** including reordered keywords with a receiver argument (`Cup[Int].put[Int, 1](!c, u: 2, v: 3)` gives `put(&c, i64, 1, 3, 2, 0)`).
- **Generic calls nested:** as receivers (`id(b).get()`, `id(Cup(v: 1)).put[Int, 1](2, 3)`), and as arguments of generic calls.
- **Receivers through handles and borrows:** `*T`, `?T`, and `!T` receivers, and weak-upgraded handles.
- **Emitted type names:** correct for `*T`, `~T`, `T?`, `Vec[*Cell[Int]]`, `[N]T` (inferred), plain function types (`*const fn`), owned closure types (`*rig.RcBox(rig.Closure(...))`), enums, module-qualified types (`lib.Point`, `Vec[lib.Point]`), and `Void`. `T!` and slice or array type arguments are rejected in expressions with Rig diagnostics.
- **Zig name collisions:** type parameters named `fn`, `var`, `anytype`, `comptime`, `rig`, `std`, `u8`, `i64`, `usize`, `bool`, `void`, `noreturn`, `panic`, `main`, `print`, or `Vec` are escaped or renamed (`@"rig'"`, `main_1`). A method type parameter named like a sibling method is renamed (`get_2`). Shadowing a module-level name, the enclosing type's parameter, or a local is rejected.
- **Compile-time values:** emitted with the right Zig type: Int at the i64 extremes, U64 max, I8 min, Float given an Int literal (`fl(3)`), an inexact Float literal rejected, enum values (`.b`, `Mode.a`), strings, and bools. Run-time arithmetic on a ct parameter panics on overflow (`rig.rt(n) + 1`), as it should. Array sizes cannot name a ct parameter: the grammar takes only integer literals, so that case does not arise.
- **Functions with compile-time parameters as values:** rejected everywhere I tried: bare names, `Type.m`, `module.f`, `module.Type.m`, typed bindings, arguments, fields, arrays, and returns. So are `f[Int]` and `check[1]` used as values.
- **Generic bodies:** `==` and `<` requirements hold, `%`, `-`, and `<<` on `T` behave, a literal next to `T` in a call is conservatively rejected, and resource `T` is moved and dropped leak-free. `T!` and `T?` returns work. Recursion and mutual recursion between generic functions work, and polymorphic recursion is reported.
- **Performance:** checking stays near-quadratic in nesting depth: depth 200 of `id(...)`, `Box(v: ...)`, `max(..., 1)`, and method chains each check in about 0.1 s. I found no exponential paths. `instTarget` over long `a.b[0].c[1]...` chains is O(depth^2), which is harmless.
- **Keying:** `instances` and `generic_calls` use the standard `recordKey`. `generic_calls` is keyed by the call node, except for a statement `f[Int]`, where it is keyed by the bracket node; INTERNALS documents this.
- **docs/INTERNALS.md:** the new Generics section, the `instanceOf` / `calleeOf` / `genericCallOf` table rows, the `tparams` IR description, and the emit bullets (`fn times(self: Scale, comptime n: i64)`, `max(i64, 3, 7)`, `show(3)`) match the code and the emitted output. Its only gap is that it does not mention the Scan limitation behind F2.
- **Grammar:** no conflicts, and the parser regenerates identically.
