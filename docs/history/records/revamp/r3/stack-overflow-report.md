# stack_overflow_recursion exit 139 (release, Linux x86_64)
Reproduced on pup: --release gave rc 139 in 30/30 runs (debug 134; macOS release 134).
Root cause (core file, gdb): the 8 KB frame makes dive call compiler_rt zig_probe_stack. The fault is inside the probe with rsp already in the guard. onOverflow printed the message, restored Zig's handler and returned; Zig's handler (RESETHAND) walked the stack with the DWARF unwinder from the probe pc, read CFA at rsp+k inside the guard (SelfUnwinder.nextInner:223), and faulted in the handler -> default action -> 139. Output: only the message, "Segmentation fault at address", and the zig_probe_stack line.
Fix (PR draft, branch stack-overflow-139): onOverflow calls the previous handler directly, stays installed with NODEFER, and aborts on a nested fault. After fix: 134 in 5/5 release, 5/5 debug on pup; tools/check 1 passes on Mac.
Why intermittent on burst: unknown; here it was 30/30 (possibly the fault lands in dive's own body rather than the probe on other builds/kernels).
Separate finding: --release=fast of this test never terminates on Mac and pup (100% CPU, tiny RSS, never overflows): the optimizer folds the recursion into a loop. The Mac PID 60750 was this case (my loop's second mode), not --release. The test only builds `# release`, so no impact; the "no build can fold" comment in the test is wrong for fast. An extra sigaltstack attempt did not change this.
